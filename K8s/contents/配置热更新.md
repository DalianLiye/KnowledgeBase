# 关于配置热更新
配置热更新（Hot Configuration Reload）就是不重启应用/容器，就能把新配置加载到运行中的进程里并生效\
传统方式：改配置 → 重启服务 → 新配置生效（有 downtime）\
热更新：改配置 → 不重启 → 几秒内新配置生效（无 downtime）


# ConfigMap和配置热更新
修改ConfigMap配置后，能否同步至Pod容器内，分以下使用场景：

- **Volume整目录挂载**\
  配置变更可同步\
  Volume整目录挂载实际上是挂载一个 “会自动换底层目录”的特殊目录，目录里的文件全是软链接\
  kubelet周期性（默认约 60s）同步缓存，变更延迟取决于同步间隔

- **subPath**\
  配置更新不会同步\
  subPath单独挂载的文件在Pod启动后直接一次性复制到容器，后续ConfigMap如何更新都与该文件无关

  替代方案：
  将ConfigMap挂载至容器独立空目录（如/configmap/nginx/），原目录/etc/nginx不受挂载覆盖\
  再在/etc/nginx中创建软链接指向挂载目录里的配置文件

  若目标路径原有配置文件阻碍软链接创建，可通过初始化容器提前删除原文件（不推荐PostStart，易与容器启动命令冲突）\
  示例：nginx.conf挂载到/configmap/nginx/nginx.conf，在/etc/nginx/建立软链接指向该文件，依托目录挂载实现配置自动更新

- **环境变量注入**\
  配置更新不会同步\
  从ConfigMap/Secret注入的环境变量在Pod启动时固化，后续修改资源配置无法自动更新环境变量，需重建Pod生效


# 示例

- **示例1：** 通过edit命令直接修改configMap\
  修改db.properties里的value值，执行命令：
  ```shell
  kubectl edit configmap test-dir-config
  ```
  eidt之后，进入容器内部后，需要过一段时间(更新时间+缓存时间)，会发现configmap挂载到容器内部的db.properties文件里的值也被更新


- **示例2：** 通过replace替换\
  由于configmap的创建通常都是基于文件创建的，并不会编写yaml配置文件\
  因此修改时也是直接修改配置文件，而replace是没有--from-file参数的\
  因此无法实现基于源配置文件的替换，可以通过以下方式实现\
  configmap是根据宿主机上的db.properties文件创建的，先修改宿主机的该文件，然后再执行以下命令：
  ```shell
  kubectl create cm test-dir-conig --from-file=db.properties --dry-run -o yaml | kubectl replace -f-
  ```
  注：该命令的重点在于--dry-run参数，该参数的意思打印yaml文件，但不会将文件发送给api server，再结合-o yaml输出yaml文件就可以得到一个配置好但是没有发给apiserver的文件，然后再结合replace监听控制台输出得到yaml数据即可实现替换
